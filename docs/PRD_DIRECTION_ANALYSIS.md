# TieLink 新方向规格文档：垂直深耕 vs 横向泛化

> 版本：v1.0 ｜ 日期：2026-11-22 ｜ 角色：产品通
> 性质：方向分析 + 新功能规格（PRD）

---

## 0. 结论先行

**推荐：留在垂直赛道，做「求职时间轴 Agent」—— 把求职过程本身变成可回放、可分析、可预测的数据资产。**

一句话理由：TieLink 的差异化不在"AI 能聊"，而在**求职闭环的结构化数据**（JD、简历版本、面试记录、投递状态、时间戳）。这是纯聊天框产品没有的东西。垂直方向上，这份数据的时间维度还几乎没被挖掘；横向方向上，这份数据的价值会随领域切换而清零，只剩一个通用 Agent 框架——而通用框架赛道上是 Manus、Coze、扣子空间们在打仗，个人/小团队没有胜算。

以下先给两个维度的完整分析，最后给推荐方向的具体功能规格。

---

## 1. 现状盘点（分析的地基）

TieLink 已有的能力，按"数据资产"视角重新归类：

| 环节 | 已有能力 | 沉淀的数据 |
| --- | --- | --- |
| JD 输入 | JD 解析、靶向匹配 | 岗位要求结构化数据、匹配得分历史 |
| 简历 | 导入、改写、量化、版本管理 | 简历多版本 diff、每版针对的 JD |
| 面试 | 多角色模拟面试 | 面试对话记录、每题问答 |
| 投递 | 追踪看板 | 公司、岗位、状态、时间线 |
| 记忆 | Agent Workspace 文件 | 用户求职上下文 |

**关键观察：每一类数据都带时间戳，但没有任何功能消费"时间"这个维度。** 用户求职 3 个月，TieLink 记录了一切，却回答不了："我哪类 JD 匹配度普遍偏低？""模拟面试到第几次之后通过率上来了？""我投递后的平均响应周期是多久？"

这就是新功能最大的空档，也是维度一创新的核心线索。

---

## 2. 维度一：垂直求职 Agent 的创新空间

### 2.1 候选创新方向

**A. 求职时间轴/战役复盘（推荐，详见第 4 节 PRD）**
- 做什么：把简历版本、投递、面试、反馈全部放进一条可回放的时间轴，AI 定期做"战役复盘"——回答"我这个月求职卡在哪"。
- 为什么新：所有竞品都在做"单点工具"（改简历、练面试），没人做"求职过程的元认知"。类比：Keep 记录的不是跑步动作，是配速随时间的变化。
- 前景：差异化强、数据壁垒随使用加深（换 App 等于丢掉 3 个月求职档案，迁移成本极高）。
- 风险：需要用户持续记录投递结果，依赖打卡习惯；数据稀疏期（刚开始用）体验需兜底。

**B. 模拟面试多模态升级（语音 + 摄像头）**
- 做什么：从文字面试升级为语音/视频面试，AI 分析语速、停顿、眼神、微表情并给报告。
- 为什么新：真面试是口头+面对面的，文字模拟与现实脱节。
- 前景：体验提升明显，但技术上（端侧 ASR/TTS/人脸分析）成本高，且大厂（面试鸭、ReadyTrAIn 类产品）已入场。
- 风险：工程量对当前团队规模偏大，且属于"体验优化"而非"结构创新"。

**C. 求职情报 Agent（公司/岗位市场监控）**
- 做什么：盯目标公司 JD 变动、新岗位、HC 情况，主动推送"你收藏的公司放新岗了"。
- 为什么新：把 Agent 从"被动响应"升级为"主动哨兵"，符合 Agent 主动性的行业趋势。
- 前景：真实痛点强（用户每天刷 BOSS 直聘是重复劳动），但依赖外部数据源——没有招聘平台 API 就是硬伤，爬虫有合规风险。
- 风险：数据源是生死门，不可控。

**D. Offer 决策/谈判教练**
- 做什么：拿到 offer 后输入薪资包，AI 结合市场行情、城市生活成本、当前职级做对比分析和谈判话术。
- 为什么新：求职链路的最后一公里几乎无人覆盖，且此刻用户付费意愿最高。
- 前景：单点价值高，但使用频次极低（一人一年可能只用 1-2 次），适合作为功能而非产品主线。

### 2.2 垂直赛道的整体判断

- **市场**：求职工具市场足够大（每年千万级应届生+跳槽人群），但付费天花板有限——求职是低频一次性事件，用户"上岸即卸载"。这是垂直方向最大的结构性问题。
- **护城河**：不在模型（大家都在调 API），在**求职过程数据的积累深度**和**闭环完整度**。TieLink 的本地优先架构（离线 NLP + 本地记忆）在此是加分项：求职档案的隐私敏感度高，"数据不出设备"本身可以成为卖点。
- **创新空间**：行业普遍卷"生成质量"（简历写得更漂亮），没人卷"过程数据"。这是维度一真正的空白区。

## 3. 维度二：横向泛化方向

### 3.1 可泛化什么

TieLink 真正可复用的资产是它的**目标推进 Agent 框架**：
- 目标 → 计划 → 任务拆解 → 工具调用 → 富卡片结果 → 长期记忆 → Supervisor 检查健康度/识别阻塞/重规划

这套框架本质上是"**目标达成型 Agent**"，理论上映射到任何"长周期、多阶段、有产物"的目标：

| 泛化方向 | 目标 | 与求职的映射 |
| --- | --- | --- |
| 考研/考公 | 上岸 | JD→招生简章，简历→复习计划，模拟面试→真题模考，投递→报名/志愿 |
| 留学申请 | 拿 offer | JD→项目要求，简历→文书/CV，模拟面试→院校面试，投递→网申 |
| 销售/商务 | 成单 | JD→客户需求，简历→方案，模拟面试→谈判演练，投递→客户跟进 |
| 项目申报/买房等低频大事 | 完成申报/成交 | 结构相似但工具链要重建 |

### 3.2 泛化方向的诚实评估

**优势：**
- 解决了垂直赛道的"上岸即卸载"问题——一个目标结束，下一个目标进来，用户生命周期变长。
- 框架一旦跑通，新领域主要是换 prompt、换工具链、换数据 schema，边际成本低。

**劣势（更重）：**
1. **通用框架不是壁垒**：Coze、扣子空间、Manus、Dify 都在做"目标型 Agent"的底座，泛化后 TieLink 是在跟平台型产品竞争"框架"，而不是跟工具型产品竞争"场景"。小团队打平台没有胜算。
2. **领域知识清零**：TieLink 的 NLP 匹配引擎（TF-IDF + BERT embedding + 关键词分类）是为简历-JD 匹配定制的，换个领域就要重做。求职场景积累的 prompt、评估体系、数据全部作废。
3. **每个新领域都有各自的垂直玩家**：考研有粉笔/研途宝，留学有启德/指南者。泛化后是"每个领域都比垂直玩家浅"的窘境——样样通、样样松。
4. **AI 工作台心智已清晰**：README 里"聊天不是终点，是推进下一步动作的入口"这个心智在求职场景里成立，泛化后这个叙事反而稀释。

### 3.3 维度二结论

横向泛化在"框架复用"上诱人，但它把 TieLink 从"有数据的场景产品"降级为"没数据的框架产品"。**除非找到数据结构高度同构、且你本人有领域认知的新场景，否则不建议整体转型。** 一个折中思路：留学申请是唯一值得单独评估的方向（目标/材料/网申/面试结构与求职几乎同构，用户画像重叠——应届生），可作为二阶段验证"框架可迁移性"，而不是现在的主方向。

## 4. 推荐方向的新功能规格（PRD）：求职时间轴 Agent

### 4.1 背景与问题

用户求职周期通常 1-6 个月，过程中产生的所有数据（简历版本、匹配得分、面试记录、投递状态）都散落在 TieLink 的各个模块里。用户只能"向前看"（下一步做什么），无法"回头看"（这段时间哪里出了问题）。求职本质是一个需要迭代的搜索过程，但没有复盘工具帮用户迭代。

### 4.2 目标

- 用户问题：求职数周无进展时，不知道瓶颈在简历、面试还是投递策略。
- 业务目标：提升留存（复盘产生周期性回访）+ 加深数据壁垒（时间序列数据不可迁移）。

### 4.3 用户故事

1. 作为求职者，我希望看到我全部求职事件的时间轴，以便回顾每个节点发生了什么。
2. 作为求职者，我希望 AI 告诉我"我的瓶颈在哪一环"，以便针对性改进而不是盲目海投。
3. 作为求职者，我希望每周收到一次自动复盘，以便不必主动想起才会反思。
4. 作为求职者，我希望看到匹配得分随简历版本的变化，以便知道改简历是否真的有效。

### 4.4 范围（In Scope）

- **P0 时间轴视图**：按时间聚合简历版本、匹配分析、模拟面试、投递状态变更，支持筛选（按公司/环节/时间段）。纯本地数据聚合，不依赖新数据源。
- **P0 AI 复盘**：基于时间轴数据生成结构化复盘——数据摘要（投递量/面试转化率/得分趋势）→ 瓶颈诊断（哪一环转化率最低）→ 下周建议（3 条以内的具体动作）。入口：工作台对话"帮我复盘"，+ 每周自动提醒。
- **P1 转化漏斗**：投递 → 约面 → 初试 → 终试 → offer 的个人漏斗视图，与时间轴联动。
- **P1 得分趋势图**：某 JD 类型的匹配得分随简历版本演进折线。

### 4.5 Non-goals（明确不做）

- 不做简历/面试工具本身的改造（复用现有能力，只消费其产物数据）。
- 不做外部招聘数据接入（情报监控是另一个功能，数据源风险不引入本功能）。
- 不做跨设备同步（延续本地优先架构）。
- 不做"求职成功预测"等模型类能力——数据量不足时预测是负体验。

### 4.6 数据与指标

| 层级 | 指标 | 基线 | 目标 |
| --- | --- | --- | --- |
| 北极星 | 周复盘后 7 日内产生新求职动作的用户占比 | 待上线测 | ≥ 40% |
| 驱动 | 复盘功能周使用率 | 0 | ≥ 30% 活跃用户 |
| 驱动 | 时间轴人均回看次数/周 | 0 | ≥ 2 |
| 健康 | 复盘生成失败率 | — | < 2% |

### 4.7 技术要点与风险

- 数据已齐（Room 5 张表 + AgentWorkspace 记忆文件），核心工作是**事件聚合层**：把各表按时间戳抽成统一 `CareerEvent` 流。无新表也可实现（视图层聚合），若要索引效率可加一张物化事件表。
- 风险 1：数据稀疏。新用户只有 2 条投递时，复盘必须降级为"引导补全数据"而非硬生成空分析——**宁可不分析，不做零幻觉分析**。
- 风险 2：诊断措辞。AI 指出"你面试转化率低"可能引发挫败感，复盘文案需"先讲事实，再给动作，不做人格评判"。
- 风险 3：隐私。时间轴集中呈现全部求职史，需注意导出/截图场景的脱敏提示。

### 4.8 里程碑建议

1. 第一阶段：`CareerEvent` 聚合层 + 时间轴只读视图（纯展示，验证数据形态）。
2. 第二阶段：AI 复盘接入（对话入口 + 每周提醒）。
3. 第三阶段：漏斗/趋势图 + 复盘建议与"下一步行动"打通（复盘结果直接变成 Agent 任务）。

## 5. 两维度对比总表

| 维度 | 垂直深耕（时间轴 Agent） | 横向泛化（目标型 Agent 平台） |
| --- | --- | --- |
| 数据资产 | 增值：时间序列数据不可迁移 | 清零：换领域数据无用 |
| 竞争位置 | 工具型竞品均未覆盖"过程复盘" | 正面对撞 Manus/Coze 等平台 |
| 边际成本 | 低（数据已存在，只加消费层） | 高（每个领域重做工具链） |
| 用户生命周期 | 中（可延展到"入职后成长"，但仍是低频场景） | 长（一个目标结束换下一个） |
| 风险 | 数据稀疏期体验、习惯依赖 | 每个领域都比垂直玩家浅 |
| 判断 | ✅ 主方向 | ⚠️ 二阶段可单点验证留学申请 |

**最终建议**：先做时间轴 Agent 把垂直数据壁垒做深；框架层保持模块化（`CareerEvent` 聚合层本身就是泛化的第一块砖——未来换领域只需换事件 schema），为可能的泛化留门，但现在不转身。
