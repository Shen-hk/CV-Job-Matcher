# 本地 NLP 简历岗位匹配方案复盘与策略分析

## 1. 背景

项目中设计了一套轻量本地 NLP 匹配方案，用于分析简历与岗位 JD 之间的匹配程度。方案结合了 CJK 分词、关键词匹配、TF-IDF、余弦相似度以及 TFLite BERT Embedding，在离线场景下输出简历与岗位的综合匹配分，并提供命中项、缺失项、证据句和置信度等可解释信息。

这套方案的初衷不是替代云端大模型，而是在无法稳定依赖网络、存在隐私合规要求、需要低成本批量运行或需要结果可复现时，提供一套本地可运行的匹配能力。

## 2. 当前方案做了什么

当前方案主要完成了以下工作：

1. 对简历和岗位 JD 文本做基础清洗与归一化，降低大小写、符号、技术词写法差异带来的影响。
2. 使用 CJK 分词处理中文、英文和技术名词混合文本，提取候选关键词和技能项。
3. 使用关键词匹配计算岗位要求在简历中的覆盖情况，输出命中技能和缺失技能。
4. 使用 TF-IDF 给词项分配权重，降低通用词影响，提高关键技术词、业务词和岗位要求词的权重。
5. 使用余弦相似度比较简历文本向量和岗位文本向量的整体相关性。
6. 引入 TFLite BERT Embedding 做本地语义向量计算，补充传统关键词和 TF-IDF 无法识别的同义表达、近义表达和语义相似关系。
7. 将关键词分、文本相似度分、语义向量分和规则分进行融合，形成综合匹配分。
8. 输出可解释结果，包括命中项、缺失项、证据句、评分组成和置信度。

整体上，它更像是一个本地搜索和推荐排序管线，而不是一个单纯的 AI 问答功能。

## 3. 方案价值

本地 NLP 匹配方案的主要价值在于工程可控性：

1. 离线可用：即使没有网络或不能调用云端 API，也能完成基础匹配。
2. 隐私友好：简历、联系方式、薪资、公司经历等敏感信息不需要上传到第三方服务。
3. 成本稳定：适合大批量简历与岗位匹配，不会随着调用量增加产生高额模型 API 成本。
4. 结果可复现：同一份简历和 JD 在同一套规则下可以得到稳定结果。
5. 可解释：可以明确展示哪些技能命中、哪些要求缺失、证据来自哪一句。
6. 易结合业务规则：可以加入年限、学历、城市、行业、技术栈优先级等硬性条件。

因此，这套方案适合私有化部署、端侧运行、内网环境、批量初筛和对解释性要求较高的招聘辅助场景。

## 4. 关键问题：关键词误命中与否定语义误判

当前方案存在一个非常重要的问题：如果只做关键词匹配、TF-IDF 或余弦相似度，很容易把“出现过的词”误认为“候选人具备的能力”。

典型例子：

```text
精通 Java，但是不了解 Kotlin。
```

如果系统只是判断关键词是否出现，那么会得到：

```text
Java: 命中
Kotlin: 命中
```

但真实语义应该是：

```text
Java: 正向命中，熟练度高
Kotlin: 被否定，不应计入正向技能，甚至应该标记为缺失项
```

这说明单纯依赖关键词、TF-IDF 或文本相似度是不够的。它们能判断“Kotlin 出现了”，但不能稳定判断“候选人不了解 Kotlin”。这是当前本地匹配方案中必须正视的缺陷。

## 5. 问题根因

这个问题的根因主要有四类：

1. 词项匹配缺少上下文理解
   关键词匹配只知道某个词是否出现，不知道它出现在肯定、否定、转折还是弱经验语境中。

2. TF-IDF 只看统计权重
   TF-IDF 可以判断一个词是否重要，但无法判断这个词是被肯定还是被否定。

3. 余弦相似度只能衡量整体相似
   如果简历和 JD 都出现了 Kotlin，余弦相似度可能会升高，即使简历表达的是“不了解 Kotlin”。

4. Embedding 语义相似度解释性不足
   BERT Embedding 可以提升语义理解能力，但如果直接用整段文本算相似度，仍然可能被局部否定表达干扰，而且很难解释具体哪个技能是正向还是负向。

所以，问题不是某一个算法写错了，而是“技能是否具备”本身不是简单的文本出现问题，而是一个结构化语义抽取问题。

## 6. 改进策略

后续应该把技能识别从简单的关键词命中升级为：

```text
技能项 + 证据句 + 极性 + 熟练度 + 置信度
```

例如：

```json
{
  "skill": "Java",
  "polarity": "positive",
  "proficiency": "expert",
  "evidence": "精通 Java",
  "confidence": 0.92
}
```

```json
{
  "skill": "Kotlin",
  "polarity": "negative",
  "proficiency": "unfamiliar",
  "evidence": "不了解 Kotlin",
  "confidence": 0.88
}
```

### 6.1 增加否定词识别

需要识别常见否定模式：

```text
不了解、不熟悉、不会、未接触、没有经验、缺乏经验、经验不足、不是主要技术栈
```

当技能词附近出现这些表达时，不应将该技能计为正向命中。

### 6.2 增加程度词识别

同一个技能在不同表达下应有不同权重：

```text
精通 Java      -> 高权重
熟悉 Java      -> 中高权重
掌握 Java      -> 中高权重
使用过 Java    -> 中等权重
了解 Java      -> 低权重
学习过 Java    -> 较低权重
不了解 Java    -> 不加分或负向标记
```

这样可以避免“了解”和“精通”被打成同一档。

### 6.3 使用句子级证据，而不是全文级命中

错误方式：

```text
全文包含 Kotlin -> Kotlin 命中
```

改进方式：

```text
找到包含 Kotlin 的句子 -> 判断该句子的语义极性 -> 再决定是否命中
```

例如：

```text
证据句：精通 Java，但是不了解 Kotlin。
Java: positive
Kotlin: negative
```

### 6.4 处理转折结构

需要重点处理以下转折词：

```text
但是、但、不过、然而、只是、仅、除...外
```

例如：

```text
主要使用 Java，不过 Kotlin 只在课程中接触过。
```

此时 Java 应为强正向，Kotlin 应为弱经验，而不是同等命中。

### 6.5 增加弱经验识别

很多简历会出现模糊表达：

```text
了解 Kotlin
接触过 Go
学习过 Docker
课程项目中使用过 Vue
对 Kubernetes 有一定了解
```

这些不应直接等同于“熟练掌握”。应该归为弱命中，并降低权重。

### 6.6 使用轻量模型做二次判别

规则可以覆盖高频模式，但复杂表达会越来越多。更稳妥的方式是：

1. 先用词典和分词召回候选技能。
2. 为每个技能抽取证据句。
3. 用规则或轻量分类模型判断技能极性和熟练度。
4. 对低置信度样本再交给 LLM 或人工确认。

在离线场景下，可以考虑训练或微调一个轻量 TFLite 分类模型，用来判断：

```text
positive / negative / weak / irrelevant
```

这样比单纯用 Embedding 相似度更适合解决“是否真的掌握某技能”的问题。

## 7. 评分策略调整

原来的评分方式如果是：

```text
技能出现 -> 加分
```

应该调整为：

```text
技能出现 -> 抽取证据句 -> 判断极性和熟练度 -> 根据结果加权
```

建议评分逻辑：

```text
强正向命中：满额加分
普通正向命中：正常加分
弱经验命中：少量加分
否定命中：不加分，必要时计入缺失项
冲突表达：降低置信度，进入人工或 LLM 复核
```

示例：

```text
岗位要求：Kotlin
简历证据：不了解 Kotlin
评分结果：Kotlin 不加分，标记为缺失项
```

```text
岗位要求：Java
简历证据：精通 Java
评分结果：Java 高权重加分
```

## 8. 与直接使用 AI Prompt 的关系

直接使用 AI Prompt 的确可以更快完成语义判断。例如把简历和 JD 发给大模型，让它返回匹配分、命中项、缺失项和证据句。这种方式适合 MVP、小规模在线工具和对隐私要求不高的场景。

但本地方案仍然有意义，前提是目标场景明确：

```text
离线运行
隐私敏感
低成本批量处理
结果稳定可复现
可解释和可调参
私有化部署
```

更合理的架构不是二选一，而是混合：

```text
本地算法负责批量初筛、硬性条件判断、基础解释
AI 负责复杂语义判断、冲突表达复核、自然语言总结
```

例如：

```text
本地系统从 10000 份简历中筛出 Top 100
再调用 AI 对 Top 20 做精排和深度解释
```

这样能兼顾成本、速度、隐私和语义理解能力。

## 9. 复盘结论

这套本地 NLP 匹配方案的方向是有价值的，但不能把关键词出现等同于技能具备。尤其在简历场景中，否定表达、弱经验表达、转折表达非常常见。如果不处理这些语义结构，系统会出现明显误判。

因此，后续优化重点不是继续堆更多关键词，而是把匹配对象从“词”升级为“带上下文的技能证据”。

最终目标应从：

```text
这个词有没有出现？
```

升级为：

```text
这个技能是否被正向证明？
熟练度是什么？
证据句在哪里？
置信度有多高？
是否存在否定或冲突表达？
```

只有完成这一步，本地简历岗位匹配系统才算从关键词搜索升级为可解释的语义匹配分析。

## 10. 面试或项目汇报表达

可以这样总结：

```text
这个项目最初采用 CJK 分词、关键词匹配、TF-IDF、余弦相似度和 TFLite BERT Embedding 来做简历与岗位的本地匹配分析。这样做的好处是离线可用、成本低、可解释、适合隐私敏感场景。

但复盘后我发现，单纯的关键词命中存在明显风险。例如简历中写“精通 Java，但是不了解 Kotlin”，简单匹配会把 Kotlin 错误识别为候选人具备的技能。因此我把后续优化方向调整为证据句级别的技能抽取，不再只判断技能词是否出现，而是为每个技能识别证据句、极性、熟练度和置信度。

具体策略包括否定词识别、程度词识别、转折结构处理、弱经验识别，以及必要时引入轻量分类模型或 LLM 复核。这样可以让本地匹配系统既保留离线和可解释优势，又减少关键词误命中的问题。
```
