# 主 Agent：后台委托与结果交付规格

> 讨论稿｜2026-11-24  
> 依据：[产品 PRD](AGENT_ORCHESTRATION_PRD.md) · [交互规格](AGENT_INTERACTION_SPEC.md)  
> 定义目标行为、实现边界和验收，不代表当前应用已支持后台执行。Figma 仍只使用 `9Wp2MFkHvQhRoWPA1IQ2RN`。

## 1. 核心场景与本轮决定

用户说出一个灵感并交给主 Agent。主 Agent 将灵感整理成这次能交付的结果，调用合适的团队或工具；用户离开聊天、切换应用或锁屏后，任务继续推进。通知栏呈现当前步骤，结果回到原对话，用户回来后继续修改。

用户已明确：只要求手机正常运行时，应用放到后台后继续做，并能从通知看到当前进度与阶段成果。关机期间执行不属于需求，不为此扩展服务端执行架构。以下界面、运行控制与异常细节按该方向确定。

团队承载可复用的工作方式，用户可以创建和定制。用户始终面对主 Agent，不需要分别与每个角色交谈，也不需要先生成团队才开始。运行中的团队是执行力量，不新增一个必须常驻的前台界面。

| 问题 | 本轮决定 |
| --- | --- |
| 用户必须说出完整需求吗 | 不必；非关键偏好用明确的默认假设，先交付有用的第一稿 |
| 说灵感就必定执行吗 | 区分委托、讨论和仅记录；明确委托直接开始，有歧义只澄清关键意图 |
| 必须先审阅整套计划吗 | 普通读取和生成新草稿不需要；新增影响、授权缺口或歧义才等待决定 |
| 需要用户点击后台模式吗 | 不需要；任务接下后即由独立执行器负责，离开页面不取消 |
| 没有自建团队怎么办 | 主 Agent 使用合适的预置能力或直接组织已接入工具 |
| 工作时还能聊天吗 | 可以；补充要求关联任务，闲聊直接回复，新工具任务排队 |
| 首版是否并行运行多个任务 | 不并行；全局单执行位和持久队列，等待用户、系统条件或暂停时释放执行位 |
| 何时宣布完成 | 约定交付物可靠保存、可打开且版本一致后；建议文字和工具开始都不算完成 |
| 通知能看到哪些成果 | 展示最近已完成成果的简短摘要，展开可看阶段清单，点击打开已保存版本；后台继续执行 |

## 2. 灵感怎样成为任务

### 2.1 意图与默认行为

| 用户表达 | 默认响应 |
| --- | --- |
| “我想到一个面试复盘助手，帮我先整理成一页方案” | 接下草稿任务，说明交付约定与假设，直接推进 |
| “用我的简历团队，把这份材料改好并生成 PDF，我先去忙” | 绑定资料和团队版本，接单后执行支持的步骤，不要求保持页面打开 |
| “我有个想法：面试复盘助手，你觉得呢” | 先讨论，不自动建立长时间工具任务 |
| “只把这个灵感记下来” | 按明确范围保存记录，不启动方案生成或组队 |
| “帮我把这个做出来”且上文有明确的一页方案要求 | 沿用已有上下文；不把“做出来”擅自扩大为开发、上线和运营 |
| “帮我做出来”但没有明确产物或可用上下文 | 给出一个可操作的范围澄清，例如先出方案还是修改现有材料 |

接单时记录一份可编辑的交付约定：目标、交付物及格式、引用资料版本、关键约束、完成标准、默认假设、允许动作、执行预算。它呈现为简短摘要，可展开查看，不要求用户填写表单。

用户对新草稿的委托包含在任务空间持久化草稿的授权；不由此取得覆盖原简历、采用为正式版本、发布网页或对外发送的授权。保存团队配置也不启动业务任务。

### 2.2 澄清与先做的边界

- 版式、语气、草稿名称等非关键偏好：先用合理默认，接单摘要说明，允许随时修改。
- “一页方案”缺少用户画像：可以列为假设，输出适用对象和待验证问题，不把假设写成已确认事实。
- 简历缺少真实经历、岗位分析缺少 JD：不能编造事实。只在现有资料足以产生独立成果时先做；依赖缺口的步骤等待补充。
- 缺少工具或后台执行能力：接单前说明能交付和不能交付的部分；用户原有完整要求保留，改变范围不能静默发生。
- 没有模型、额度不可用或资料无法读取：说明缺口，保留原始想法和输入；不显示“团队已在后台处理”。

### 2.3 示例对话

> 用户：我想到一个面试复盘小助手，先帮我整理成一页方案，等会儿看。
>
> 主 Agent：我先按个人求职场景整理，包含使用流程、核心功能和待验证问题。任务已接下，你可以去忙，结果会留在这里。
>
> 任务卡：面试复盘助手方案｜正在整理流程 · 第 2/4 步｜查看进度 · 暂停
>
> 完成提醒：结果已准备好，点击查看。
>
> 主 Agent：一页方案已完成。关键假设是用户手动提供面试记录；录音和外部日历接入列为后续验证项。
>
> 用户：加上每次面试结束后的反思问题。
>
> 主 Agent：我会在这份方案中补充复盘问题，生成新版本。

这是目标交互示例；通用文档工具尚需接入，不能把示例作为当前能力清单。

## 3. 接单、执行与可靠交付

~~~mermaid
sequenceDiagram
    participant U as 用户
    participant M as 主 Agent / 聊天
    participant S as 持久任务与事件
    participant E as 独立执行器
    participant T as 团队与工具
    participant N as 系统通知
    U->>M: 提出灵感并委托
    M->>S: 保存目标、输入版本与执行请求
    S-->>M: 接单已持久化
    M-->>U: 已接下 / 已排队，可离开
    E->>S: 领取任务并取得执行权
    loop 按依赖执行步骤
        E->>T: 调用工具与交接产物
        T-->>E: 实际结果或明确错误
        E->>S: 保存产物、步骤状态与检查点
        S-->>N: 静默更新当前步骤与已保存阶段成果
    end
    E->>S: 核验完成标准，保存交付记录
    S-->>M: 原会话出现唯一交付消息
    S-->>N: 结果已准备好
    U->>N: 点击查看
    N->>M: 打开原会话对应结果
    U->>M: 继续修改
~~~

接单记录必须先于“已接下”回复。若调度尚未成功，展示已排队或等待调度，不显示执行中。调度派发可以重试，但同一请求只能建立一个运行。

步骤只有在产物写入并核验后才计成功。临时文件不能当作正式结果；先写临时位置，成功后登记稳定版本和引用。新一版内容必须与新版 HTML/PDF 对齐，不交付不同内容版本混合的结果包。

完成流程先持久化产物与交付记录，再更新界面和通知。通知丢失不丢结果；应用恢复时可以从交付记录重建消息。通知故障不能使已经完成的业务任务重新执行。

## 4. 运行状态与调度规则

以下为目标状态，不直接替换现有求职任务枚举；实现时通过明确映射适配。

| 状态 | 进入条件 | 离开方式与执行位 |
| --- | --- | --- |
| QUEUED | 任务接下但尚未领取 | 调度后运行；不占执行位 |
| RUNNING | 持有效执行权并实际工作 | 步骤推进、等待、暂停、取消或终态；占执行位 |
| WAITING_CONSTRAINT | 无网络、系统配额或其他执行条件不满足 | 条件恢复后重新排队；不占执行位 |
| WAITING_INPUT | 缺关键资料或事实 | 用户补充后校验并排队；不占执行位 |
| WAITING_APPROVAL | 下一项操作确实需要用户决定 | 同意、调整或拒绝；不占执行位 |
| WAITING_BUDGET | 达到本轮资源上限 | 展示已有成果，由用户继续、缩范围或结束；不占执行位 |
| PAUSING / CANCELING | 用户命令已接收，当前操作尚在收束 | 到安全边界并完成核验后暂停或取消；仍占执行位 |
| PAUSED | 有可靠检查点且执行已停止 | 用户恢复后排队；不占执行位 |
| RECOVERING | 执行者消失、状态不确定或需核验操作 | 成功则补齐记录，否则按可恢复条件排队或转失败；核验时占执行位 |
| COMPLETED | 全部必需交付物通过检查 | 只读回看或开启关联修订；不占执行位 |
| PARTIAL / FAILED | 有可用成果但约定未满足 / 没有可用交付物 | 用户重试未完成部分或调整；不占执行位 |
| CANCELED | 后续执行已取消 | 不自动重启；已有成果可用于新任务，不占执行位 |

运行中断不直接当失败，也不一直保留 RUNNING；先确认是否还有有效执行者，必要时核验操作和检查点。已完成步骤只有在输入与依赖版本仍适用时才能复用。

单执行位属于应用级工具运行约束，不阻塞普通聊天。一次工具调用内部可以有自己的计算和网络线程；不因此宣称产品支持多个团队并行运行。排队默认按接单先后，用户可设“优先处理”；当前不可中断的操作先安全收束。

等待用户期间只保留已成功成果，不长期占住执行器或轮询用户。补充后重新排队；新任务已经开始时不被自动抢占。系统条件阻塞的任务也释放执行位，其他满足条件的任务仍可调度。

## 5. 进度、通知与任务入口

### 5.1 一个事实来源，三个展示位置

会话任务卡、应用内任务列表和系统通知消费同一组持久事件。事件包含任务、运行、计划版本、步骤、状态、序号、发生时间和产物引用。界面只接受当前版本且顺序有效的事件；不能让迟到的“正在执行”覆盖“已完成”。

- 默认显示“正在生成版式 · 第 3/4 步”，无可靠总步数时只显示当前动作和已完成事项。
- 步骤数不当作工作量百分比，模型输出长度不当作任务进度。首版不提供没有实测依据的预计完成时间。
- 显示最近进展时间。心跳只能说明执行者仍在，不等于完成了新步骤；等待网络不能持续显示运行动画。
- 执行详情可以展开工具名、输入引用、交接产物、耗时与错误；不把内部推理文本作为进度证据。

### 5.2 通知策略

| 事件 | 呈现策略 | 操作 |
| --- | --- | --- |
| 开始或步骤变化 | 更新同一运行通知，静默，不逐字刷新 | 暂无成果时查看进度、暂停 |
| 新阶段成果已保存 | 更新原通知中的成果摘要，不另发完成提醒 | 查看成果、暂停 |
| 队列或临时约束等待 | 应用内展示；存在通知时更新为真实等待状态 | 查看任务 |
| 需要输入 / 确认 / 增加预算 | 按用户渠道设置提醒一次，不周期催促 | 进入对应问题或变更预览 |
| 成功 | 产物和交付记录完成后提醒一次 | 查看结果 |
| 部分完成 / 最终失败 | 说明已保留成果和缺失项，提醒一次 | 查看成果、重试未完成部分 |
| 暂停 / 取消 | 收束后撤销运行态通知，应用内保留记录 | 恢复或回看 |

进度与结果提醒使用独立通知渠道角色，最终渠道设计结合 Android 版本验证。停止前台执行不代表必须删除需要处理的提醒。用户正在原会话看同一任务时抑制重复声音，后台运行所需通知仍遵循系统要求。

锁屏默认只显示通用状态，不显示姓名、公司、资料名称或正文。系统状态栏是否显示图标、通知是否折叠、勿扰时是否响铃均服从系统和用户设置，不承诺所有设备一致。

首次接下适用任务时解释用途并申请通知权限；拒绝后继续允许可执行任务，通过顶部摘要、任务列表和未读结果兜底。禁止将通知权限当作所有执行的硬前置。通知权限关闭时，具体前台服务通知的系统呈现需按版本处理，不能声称一定能在通知栏看到进度。

### 5.3 点击、已读与过期通知

- 跳转标识绑定会话、任务、运行和交付版本，打开后先读真实状态，不信任旧通知正文。
- 若问题已处理，定位最新进度或结果，不再次提交同一个确认动作。
- 点击和划除通知只影响展示或已读状态，不改变运行状态；暂停必须是明确的任务命令。
- 已完成未读与需要处理分别记录。进入对应结果视图才标结果已读，进入别的会话或只展开通知不默认已读。
- 已删除任务的旧通知给出“该任务已删除”及返回入口；不重建、不重跑，也不自动选择另一任务。
- 首版仅提供查看与暂停等明确操作，不在锁屏通知内执行正式采用、覆盖资料或外部发送。

### 5.4 进度与阶段成果的具体展示

通知承担快速了解和进入成果的入口，完整内容在应用内呈现。以“优化简历并生成 PDF”为例：

| 区域 | 展示示例 | 规则 |
| --- | --- | --- |
| 标题 | “简历优化 · 正在生成 PDF” | 任务短名与当前真实动作；长名称省略后仍可识别任务 |
| 收起态正文 | “简历草稿 v2 已完成” | 最新一项已经可靠保存的阶段成果；尚无成果时显示正在处理的内容 |
| 展开态正文 | “已完成：岗位分析、简历草稿 v2；进行中：PDF 导出” | 最多三项，已完成与进行中分开标识，不把计划描述当成果 |
| 主操作 | “查看成果” | 打开已保存成果对应版本；尚无成果时显示“查看进度” |
| 第二操作 | “暂停” | 请求安全暂停；取消放在应用内任务详情 |
| 任务完成 | “简历和 PDF 已准备好” | 全部必需交付物核验成功后才使用；点击进入完整结果 |

阶段成果不限于文件，也可以是已保存的分析结论或结构化清单；必须有对应的稳定记录与任务引用。可展示“已整理 5 项岗位要求”，不能由模型臆造数量。未完成的流式文本和临时文件不进入成果列表。

点开阶段成果时任务继续执行，预览页显示当前任务状态与“返回对话”。若用户修改阶段稿，按新的内容版本重验后续依赖；仅打开预览不触发重跑。通知引用的旧成果已被新版本替代时，默认打开最新有效成果并显示版本，历史仍可回看。

更新触发点为步骤状态变化、新成果可靠保存、需要用户处理或任务终态；合并短时间连续变化，保持同一任务通知，进度更新静默。阶段成果出现不额外弹出成功消息，真正完成或确实需要用户处理时再提醒。锁屏默认仅保留通用状态，用户解锁后可查看详情。

## 6. 用户补充、暂停、取消与删除

每条干预记录目标任务和收到时的计划版本。“突出项目经历”指向正在讨论的简历；“另外再整理一篇文章”建立排队任务；存在两个合理指代时澄清，不能猜测后同时改两份文件。

改动尚未开始的步骤时更新计划；改动已经完成的内容时建立新产物版本，重跑受影响的后续步骤。旧计划的迟到结果可留作历史，不能成为新计划的有效交付。无歧义且在已有授权内的调整不增加一轮计划审批。

暂停可恢复，取消结束本次运行；两者都不承诺回滚已发生的保存。正在提交时展示正在收束，得到结果或核验后才进入终态。取消后的新结果不得自动追加为新交付，需登记为取消期间完成的操作并说明实际影响。

删除会话时，存在运行则给出明确的取消并删除选项；不能让执行器继续持有已删除会话。先取消并核验在途操作，再清理会话私有草稿；独立保存资料按用户选择处理。删除团队配置不会破坏运行已经绑定的快照；用户撤销资料访问则阻塞后续读取，通知说明缺口。

## 7. 资源预算与失败恢复

首版需要给单次委托设上限，并在任务摘要的展开项可见。候选默认值：累计有效执行 15 分钟、总工具尝试 20 次、每步骤瞬时故障最多自动重试 2 次；具体阈值经端到端实测校准后定版。这些是停止继续消耗的上限，不是耗时承诺或费用报价。

等待网络、等待用户和排队不计有效执行时长。重试、恢复和继续步骤共用该轮预算，不能因重新进入页面重置。模型用量在提供者可取得时记录实际值，没有价格数据就不编造金额。

| 情况 | 恢复规则 |
| --- | --- |
| 网络短暂失败 | 检查工具重试语义后做有上限的退避重试；无网转等待，不紧密循环请求 |
| 模型额度不足或配置失效 | 保留成果，说明需要设置或恢复额度，不伪装成本地模型已完成通用生成 |
| 工具确定失败且可重试 | 只重试该步骤及受影响依赖，复用仍有效的上游成果 |
| 写入超时且结果未知 | 先查操作凭据或实际文件；无法证明未发生则不自动重复写入 |
| 系统回收 / 进程重建 | 核验执行权、版本与检查点；废弃旧执行者写权限后再继续 |
| 流式生成中断 | 部分文本标为未完成；按工具约定续作或生成新草稿，不盲目拼接两次输出 |
| 执行预算用尽 | 停在安全边界并交代现有成果、缺失项与下一步；用户明确选择后增加预算 |
| 下游 PDF 导出失败 | 交付可用文档和 HTML，标部分完成；只重试导出，不重新生成已核验内容 |

所有自动恢复受当前授权和原预算约束。等待用户不转为默认同意，失败不静默缩小用户要求；明确缩小范围时更新交付约定并保留变更记录。

## 8. 数据与执行一致性

以下是待设计的数据责任，不表示数据库已经具有这些表。

| 记录 | 最小责任 |
| --- | --- |
| Task / Run | 会话归属、用户原始要求、交付约定、输入及团队快照、计划版本、状态、预算、时间 |
| ExecutionRequest | 客户端请求标识、派发状态、队列顺序、优先级；同一请求只能接单一次 |
| StepAttempt / Checkpoint | 当前步骤、输入版本、依赖、尝试次数、工具能力、恢复位置、结果引用 |
| ExecutionLease | 执行者、有效期和递增执行代次，防止恢复执行者与旧执行者同时提交 |
| OperationReceipt | 幂等操作标识、提交结果和稳定产物引用；与实际写入核验关联 |
| TaskEvent | 事件序号、运行与计划版本、动作和状态；不存无必要的资料全文 |
| ArtifactVersion | 内容类型、稳定位置、源内容版本、生成步骤、校验结果、草稿或正式资料关系 |
| Delivery / NotificationOutbox | 交付版本、消息引用、未读状态、通知事件与发送状态；支持重放防重 |

同一执行代次才能提交当前步骤；旧执行者的迟到回调不能修改新运行。状态与事件采用事务或可恢复提交协议，不能假定 Room 与 DataStore 存在跨存储事务。接单落库与系统调度之间用待派发记录补偿，防止任务已接下却丢失调度。

交付记录以运行和交付版本去重，通知以事件标识去重；数据库约束保障业务只接受一次结果。系统通知发送与数据库写入不能做成一个事务，因此还需稳定通知 ID、发送标记与恢复核对，避免重放不断提醒。

后台任务和未读交付需要真实数据库迁移，不能因开发用破坏性迁移丢失用户已接下的委托。复用现有操作凭据时检查其业务范围，不能把“已采用简历”凭据直接当作“任意工具已执行”。

### 9.2 平台依据与方案选择

Android 的 WorkManager 支持持久工作，长时间 worker 可通过前台服务配合通知执行；Android 16 的长时间 worker 仍受作业配额影响，不能把它理解为永久保活。依据：[长时间 Worker 官方说明](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running)。

Android 13+ 的通知权限影响通知展示，但启动前台服务本身不以获得该权限为必要条件；启动服务仍需按要求提供通知。拒绝后需验证不同系统界面的呈现。依据：[通知运行时权限](https://developer.android.com/develop/ui/compose/notifications/notification-permission)。

后台启动前台服务受到系统限制。候选方案需要在用户发出委托时安排启动，并按实际工具耗时、服务类型及目标版本验证；不能等应用已退后台后才假定可以任意启动。依据：[前台服务启动限制](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)。

WebView 的 HTML 打印需要内容加载和打印适配器流程，已有代码直接写 PDF 文件，仍需验证没有 Activity 可见窗口时的资源与生命周期。依据：[HTML 文档打印](https://developer.android.com/training/printing/html-docs)。

待做工程验证：比较持久调度加有限执行与适用前台服务方案，明确工具对应的服务类型、权限、超时与系统额度。未验证前不拍定“所有步骤都放进一个无限运行 Service”。验证通过的工具才标注可后台运行。

### 9.3 后台执行与中断处理

| 条件 | 目标承诺 |
| --- | --- |
| 应用离开前台、手机联网、系统允许 | 支持的工具继续执行，进度与结果可查询 |
| 本机断网、系统暂停、回收、重启 | 持久化并按条件恢复；不承诺立即调度，不显示虚假的持续计算 |
| 用户强行停止应用 | 停止后不自动继续；下次打开先核验进展，再由用户恢复 |

验收聚焦应用正常切后台后的持续执行，以及通知中的真实进度与阶段成果；关机期间执行不纳入需求或后续方案设计。

## 10. 工具后台能力清单

工具注册需增加执行环境约定：是否需要可见界面、网络、文件读取范围、可取消阶段、幂等或核验方式、预期产物。能力分为“后台可运行”“需要回到应用”“尚未验证”，不由模型临时猜测。

| 工具类别 | 目标处理方式 | 完成证据 |
| --- | --- | --- |
| 已授权文本与资料读取 | 有持久读取权或任务快照时后台读取，权限撤回则等待 | 对应输入版本成功解析 |
| 文档内容生成 | 模型请求可脱离页面，由执行器持有并保存草稿 | 可读取的稳定文档版本 |
| HTML 生成 | 后台生成稳定文件，预览在用户回来后打开 | 与内容版本一致的有效 HTML |
| PDF 生成 | 现有 WebView 导出先做无页面专项验证 | PDF 可读取、页数有效，内容来源版本明确 |
| PDF 查看 | 用户打开结果后使用前台预览；后台可做程序化文件检查 | 前台打开已有文件；程序检查不冒充视觉审阅 |
| 系统文件选择、分享与另存为 | 需要用户交互时回到应用；不后台弹页面或自动选择外部目标 | 实际用户操作结果 |

接单发现某个必需工具只能前台运行时，先说明限制，任务保存到对应步骤等待回来；不能把它标成完全自主交付。完整简历 PDF 后台闭环必须在 PDF 验证通过后才能验收。首个后台闭环可先选已验证的文本草稿任务，但这不等于简历 PDF 链路也已通过。

## 11. 需要落图的状态与原型路径

| 状态 | 主要可见内容 | 关键去向 |
| --- | --- | --- |
| 灵感输入与接单 | 主 Agent 聊天、资料、交付摘要、任务卡、固定输入栏 | 执行详情或继续聊天 |
| 用户在别的会话 | 原会话不被打断，顶部紧凑任务摘要 | 跳到运行所属对话 |
| 下拉通知栏运行态 | 应用名、当前步骤、更新时间、查看和暂停 | 原任务进度 |
| 锁屏通知 | 默认隐藏任务正文，只保留通用状态 | 解锁后查看 |
| 需要补充 | 已完成成果、一个具体问题、待补资料入口 | 回答后恢复排队 |
| 结果提醒与未读 | 完成通知、原会话结果卡、产物版本 | 打开结果或继续修改 |
| 部分完成 | 可用产物、未完成项、原因、局部重试 | 只补做缺失部分 |
| 暂停、断网与排队 | 各自原因、保留成果与可用动作 | 恢复、调序或取消 |
| 通知权限拒绝 | 非阻断说明、任务入口、未读结果 | 留在当前流程 |

原型主线：聊天委托 → 接单任务卡 → 通知栏查看步骤 → 完成通知 → 原会话结果 → 继续修改；支线覆盖需要补充、拒绝权限、部分失败及暂停恢复。沿用指定文件已有组件，不增加以团队管理为主体的新首页。

## 12. 首版验收矩阵与实施顺序

| 验收场景 | 通过条件 |
| --- | --- |
| 不完整灵感明确委托 | 公开合理假设后直接生成新草稿；不编造用户事实，不要求先建团队 |
| 讨论与只记录 | 不产生未经委托的长任务，记录操作有可靠结果 |
| 切应用、回桌面、锁屏 | 在支持条件下实际完成步骤并交付；前后台切换不重启工具 |
| 继续聊天与第二项委托 | 聊天可用，补充正确关联，新任务可靠排队，未同时覆盖同一产物 |
| 需要用户处理 | 问题精确、已有成果保留、提醒一次、释放执行位；不自动同意 |
| 通知权限拒绝或渠道关闭 | 不强制返回设置，不虚称通知已展示；任务入口和未读结果可用 |
| 后台执行产生阶段成果 | 通知展示当前动作和已保存成果摘要；展开状态清晰，点击可打开正确成果版本，任务继续推进 |
| 关闭旧通知、点过期通知 | 不取消任务，不重复确认或执行，能定位当前状态 |
| 完成到达与重复点击 | 结果可打开，正确会话只出现一次交付，点击不重跑 |
| 网络中断与系统回收 | 显示实际等待或恢复状态，检查点续作不重复已成功写入 |
| 暂停或取消恰逢提交 | 显示收束过程，核验后进入准确状态，不丢失已发生操作 |
| 执行期间修改要求或团队 | 固定版本可追溯，旧结果不能覆盖新计划，受影响输出重新校验 |
| PDF 缺失或版本不一致 | 不能标全部完成；已有文档可用，局部重试不改写有效上游 |
| 预算耗尽 | 安全停下，展示已有成果与缺口，未因恢复或重试重置预算 |
| 删除会话与旧通知 | 无孤立运行，不重建已删除任务，正式资料按明确选择处理 |

建议依次实现：

1. 交付约定、输入快照与工具执行环境声明；先完成无界面的最小草稿工具。
2. 独立执行器、持久接单队列、执行权、检查点与恢复防重；保护现有求职数据。
3. 进度事件、可靠交付和应用内任务入口；确保没有系统通知仍能完成闭环。
4. 通知、深链、权限拒绝和运行控制；验证步骤与交付一致。
5. PDF 无页面专项验证、简历工具适配与端到端结果检查，再宣布支持完整链路。
6. 按 API 24 基础兼容、API 33 通知权限、API 35 当前目标限制及 Android 16 作业配额补充设备覆盖，并抽测不同厂商锁屏与省电条件。

进入开发前需定版的工程项：适用的调度及前台执行机制、实际服务类型、预算实测值、输入文件持久访问策略与 PDF 导出方案。它们不改变本轮已定的产品方向：主 Agent 接下委托，用户离开后继续推进，结果再回到用户。
