# TieLink 主 Agent、团队与工具产品 PRD

> 文档状态：讨论稿｜2026-11-24  
> 用途：作为产品与架构设计的基线，不代表相关功能已经实现。  
> 定位：以一个主 Agent 的对话为产品主体，承接灵感与任务，在用户离开聊天后按授权继续执行，通过通知和会话交付结果；团队与工具可客制化，求职是首个验证场景。  
> 本轮细化：[交互规格](AGENT_INTERACTION_SPEC.md) · [后台委托与结果交付规格](AGENT_BACKGROUND_EXECUTION_SPEC.md)。

## 1. 方向与决策

**用户始终与一个主 Agent 对话。主 Agent 理解需求、维护上下文、调用工具或专业团队、展示过程与产物，并继续推进工作。用户可以创建自己的团队，调整角色、工具和工作方式。**

**用户把一个灵感交给 Agent 后，可以去做别的事。Agent 将它整理成可执行目标，调用合适的团队或工具，在后台推进；用户可以从通知栏查看当前步骤，完成后回到原对话接收结果并继续修改。** 这是首版需要验证的核心体验，不以用户守在聊天页面为前提。

本轮范围已明确：手机正常运行，应用切到后台后继续工作；通知同时呈现“正在做什么”和“已经做出什么”。通知展开可查看阶段成果摘要，点击可打开已保存成果，任务继续推进。具体交互与异常处理由产品设计细化，不增加后台模式开关或额外启动确认。

本次修正：上一轮把“创建和运行团队”提升为首页主任务，弱化了 Agent 本身。现在明确主 Agent 是用户持续交流的对象，团队与工具是可调用、可定制的能力。用户没有创建过团队，也应能完成第一项任务。

| 层次 | 负责什么 | 用户如何接触 |
| --- | --- | --- |
| 主 Agent | 对话、意图判断、追问、上下文、调度、解释结果和下一步 | 默认聊天主体，持续承接任务 |
| 团队 | 一套专业工作方式中的角色、工具、步骤与输出偏好 | 在对话中选择、创建或调用，通过管理界面客制化 |
| 工具 | 有明确输入、输出与操作效果的具体能力 | 调用卡片、附件入口、编辑器或预览界面 |
| 专业工作台 | 复杂编辑、练习与预览 | 从对话或产物进入，完成后回到原会话和任务 |

团队可以把简历读取、岗位分析、内容编写、版式生成和 PDF 预览整合为一套能力；内部是否使用多个 Agent，取决于实际分工。一个团队也可以只有一个专业角色和多个工具。

### 1.1 用户价值

用户可以持续对同一个 Agent 说“帮我改简历”“再突出项目经历”“换一种版式”“导出 PDF”，无需重新解释资料或在每次任务前重新组队。

团队定制让用户保存自己的工作方式，例如角色职责、允许工具、常用步骤和版式偏好。以后由主 Agent 按需调用，或由用户明确指定。专业分工与工具执行可展开查看，产物有来源，用户可以继续修改。

用户也可以说“我想到一个面试复盘助手，先帮我整理成一页方案”。Agent 不要求用户先写完整需求或搭建团队，而是说明本次准备交付什么、采用哪些假设，然后推进可逆的草稿工作。非关键偏好先使用合理默认，关键资料缺失才等待补充。

### 1.2 产品边界

- 主 Agent 可以直接回答、直接调用工具或调用团队，不把组队作为所有任务的前置步骤。
- 团队角色参与实际任务交接，不能只是轮流回复同一个问题；不为增加角色而制造分工。
- 团队创建和客制化属于可选能力；普通用户无需先学习编排概念。
- 工具定制首先支持已注册工具的选择、参数和使用顺序，不等于任意代码、任意网站或外部账号操作。
- 模型建议与真实操作结果分开；具体操作的影响和已有授权决定是否需要确认。
- 首版以现有 Android 应用验证；通用能力的接入情况以代码和实际结果为准。

## 2. 用户体验与信息架构

### 2.1 主任务旅程

1. **开始对话**：用户对主 Agent 说“帮我针对这条 JD 改简历，并导出 PDF”，可以附加资料和约束。
2. **理解与补充**：识别目标、已有资料与缺口，必要时在对话内追问或展示资料选择卡片。
3. **选择能力**：直接处理、调用工具或使用合适的团队；用户也可手动指定团队。
4. **接单与执行**：任务持久化并进入执行队列后告知“已接下”；对话中展示当前动作，切换应用或锁屏后继续推进已支持的后台步骤。
5. **进度与交付**：运行通知安静更新当前步骤；完成或需要用户处理时提醒。结果自动回到原会话，以文本、文档或预览卡片呈现；复杂编辑打开专业工作台。
6. **继续交流**：用户说“再改项目经历”时，主 Agent 延续当前任务与产物上下文。

### 2.2 团队创建与客制化旅程

1. 用户说“创建一个适合我的简历团队”，或从“我的团队”进入。
2. 主 Agent 生成配置草案：用途、角色职责、允许工具、常用步骤和预期产物。
3. 用户调整成员、职责、工具、顺序或输出偏好，确认后保存团队定义。
4. 团队成为可复用能力；用户可以直接说“用我的简历团队处理这份材料”。

**创建团队与执行一次任务是两件事。** 保存配置不会自动启动任务；调用已确认的团队也不要求重新进行整套组队流程。新的资料范围和具体操作仍按当前任务处理授权。

### 2.3 产品结构

| 区域 | 入口与内容 |
| --- | --- |
| 主 Agent 对话 | 默认首页；消息流、当前任务、调用卡片、产物、固定输入栏及附件入口 |
| 任务与通知入口 | 顶部任务摘要及侧栏“任务”；查看执行中、排队、需要处理与已完成事项，点击回到所属对话 |
| 会话与任务历史 | 侧栏与历史入口；恢复会话、执行记录和产物，区分未读结果与运行状态 |
| 我的团队 | 侧栏或对话中的团队入口；创建、选择、调整角色、工具与偏好 |
| 工具与资料 | 附件菜单、侧栏和结果卡片；资料管理及专业工作台 |
| 设置 | 模型、权限和隐私配置 |

首页采用聊天界面：顶部体现主 Agent 身份和必要上下文，中部为消息流，底部保留输入栏。首次使用的示例目标是可发送的对话建议；回访时恢复会话或展示当前任务摘要。

团队、工具、资料和执行记录可以有独立管理页面，但不再以“创建 / 团队 / 运行 / 资料与工具”四项底部导航作为默认产品骨架。会话、应用内任务摘要和系统通知引用同一个任务状态，用户从任一入口都能回到原任务。

### 2.4 关键交互规则

- 调用团队后仍由主 Agent 对用户解释结果，用户可以继续提问、修改要求或停止任务。
- 主 Agent 给出必要解释；内部角色消息按需展开，避免多角色消息淹没对话。
- 新建或修改团队先生成配置草案，再确认保存；配置草案本身不执行工具。
- 已授权的读取、分析和草稿生成可直接推进；是否确认依据具体动作和已有授权，不以“是否使用团队”决定。
- 团队与计划修改形成新版本，当前任务不静默换用新配置；暂停、重试和恢复记录原因与版本。
- 区分任务草稿已持久化、已采用和已保存到正式资料，标明执行者、工具、资料来源；待确认或失败任务不计为已完成。
- 专业工作台完成操作后返回原会话和任务，主 Agent 能继续处理对应产物。
- 离开页面不会停止任务；停止、暂停与关闭通知分别表达不同意图，不混用。
- 后台工作期间输入栏仍可用；用户可以补充当前任务，也可以闲聊或提交另一项排队任务。
- 任务结果先可靠保存，再发完成提醒；用户没有点开通知也能在原会话找到结果。

### 2.5 灵感委托与离开后的体验

| 时刻 | 主 Agent 的行为 | 用户可见内容 |
| --- | --- | --- |
| 说出灵感 | 区分委托执行、讨论与仅记录；明确委托不重复要求点击“启动” | 用户原话和简短接单回复 |
| 形成任务 | 提取本次交付物、资料范围、关键约束、完成标准和默认假设 | “先整理一页方案，含使用流程和待验证问题；不涉及开发上线” |
| 开始工作 | 使用已有团队或直接组织工具；没有团队也可执行 | 对话内任务卡，显示实际采用的团队或工具 |
| 去做别的事 | 已支持步骤继续执行，不依赖当前聊天页面存活 | 通知栏显示“正在整理使用流程 · 第 2/4 步” |
| 需要补充 | 只阻塞依赖该信息的部分，保存已有成果；不编造用户事实 | “需要你补充目标岗位”，通知点击进入对应问题 |
| 任务完成 | 检查交付物可打开、版本一致且满足约定，再保存交付消息 | “方案已整理好”，结果卡与继续修改入口 |
| 回来修改 | 引用交付的具体版本形成新版本 | “再加一个复盘提醒流程”，延续原任务上下文 |

“我只是想聊聊这个想法”“只帮我记下来”不会启动后台工具任务。新鲜灵感缺少完整需求不等于不能开始：先完成有用且可逆的第一稿，标明假设和待验证项；不可替用户编造经历、数据或外部事实。通知展示步骤与最后更新时间，不暴露内部思考过程，不承诺无法测量的实时百分比。

首版采用应用内全局单执行队列：用户可以连续委托，多项任务持久化排队，实际同时推进一项；已暂停或等待用户的任务释放执行位。聊天回复可以继续，不要求用户等上一项交付才说话。并行团队调度留到后续，后台持续执行本身属于 P0。

### 2.6 通知与注意力

- 系统状态栏用于显示应用通知图标；下拉通知栏显示任务、当前步骤及最近已完成成果，例如“正在生成 PDF；简历草稿已完成”。展开后展示最多三项阶段成果摘要；有可打开成果时提供“查看成果 / 暂停”，否则提供“查看进度 / 暂停”。
- 阶段成果必须已可靠保存才展示，点击查看不停止后台工作；只有任务约定的全部交付物就绪，才从阶段进展改为完成提醒。锁屏继续遵循隐藏详情设置。
- 执行步骤静默更新同一条通知；完成、确实需要处理或最终失败才发一次提醒。用户正在对应会话查看进度时，避免重复响铃。
- 点击通知恢复正确会话、任务和待处理问题；完成通知打开结果卡，不触发重新执行。
- 首次接下适合后台执行的任务时说明通知用途，按系统要求申请权限；拒绝通知不等于拒绝任务，应用内仍可查看进度与未读结果。
- 锁屏默认隐藏任务内容和资料名称；用户可以分别管理进度、完成和需要处理通知。关闭提醒不取消任务，划掉通知不代表暂停。
- “需要处理”与“已完成未读”分别计数；红点清除不改变任务执行状态。详细文案与异常行为见后台规格。

## 3. 首发场景：把简历能力整合成团队

### 3.1 端到端示例

**用户对主 Agent 说**：“帮我针对 Android 岗位优化这份简历，生成简洁的 PDF。”

主 Agent 承接需求，检查资料并调用简历团队。下面是内部目标分工，不要求用户依次打开这些页面。

| 步骤 | 执行能力 | 职责与产物 |
| --- | --- | --- |
| 1 | 简历读取与岗位分析 | 读取用户选择的简历和 JD，形成结构化事实、岗位要求与依据 |
| 2 | 简历分析与写作 | 基于事实与岗位要求生成差距分析、修改建议和简历草稿 |
| 3 | 文档编写与 HTML 生成 | 根据简历内容与版式偏好形成文档和 HTML 版式产物 |
| 4 | PDF 生成与查看 | 按本次约定使用对应内容版本生成 PDF，提供查看入口；用户要求先审阅时才等待审阅 |
| 5 | 主 Agent | 汇总结果，并承接“再改经历”“换模板”等后续要求 |

用户可以定制“保持一页”“不虚构经历”“先给修改对照”等偏好，也可以调整角色和工具。岗位、简历、匹配、内容编写、版式与预览可以属于同一简历团队，不要求拆成多个用户必须切换的团队。

工具名称表示目标能力分类。现有简历解析、编辑和 HTML 转 PDF 是候选复用资产；通用文档编写、HTML 生成及 PDF 查看是否独立封装，需结合代码确定，不能视为已经接入。

### 3.2 工具与团队的区别

- **文档编写工具**：创建或更新文档内容，明确输出类型与保存行为。
- **HTML 生成工具**：从内容及版式要求形成 HTML，供预览或导出使用。
- **PDF 查看工具**：打开已有 PDF 检查内容和版式；生成、修改与查看分别定义。
- **简历团队**：把工具、领域角色、步骤和偏好组织成可复用工作方式，由主 Agent 按需调用。

同一工具可由主 Agent 直接调用，也可在不同团队中复用。工具不是另一个对话人格。

### 3.3 原有求职能力

简历与岗位能力优先整合为简历团队，保留原数据和专业编辑页面。模拟面试、复盘和投递追踪可作为工具或后续团队按需调用，不强制每个简历任务同时调用。

现有职业目标计划逐步适配通用任务模型，迁移不能破坏既有计划与资料。记忆和资料保留领域语义，只向当前工具或团队提供必要且已获授权的内容。

### 3.4 第二场景验证

用户对同一个主 Agent 说“把我提供的文章整理为阅读摘要”。可以直接调用工具，也可以使用阅读整理团队：整理角色产生原文要点，编辑角色基于要点形成摘要，最终回到原对话审阅。

重点验证主 Agent 保持同一对话主体、工具可跨场景复用，运行不依赖 JD 或简历字段。首版只使用用户提供文本，不假定已有网页搜索或外部数据源。

## 4. 目标架构

### 4.1 产品与能力分层

~~~mermaid
flowchart TB
    U[用户在聊天中表达需求] --> CHAT[主 Agent 对话与上下文]
    CHAT --> MAIN[主 Agent 理解、追问、选择能力与汇总]
    MAIN --> DIRECT[直接回答]
    MAIN --> TOOL[直接调用工具]
    MAIN --> TEAM[调用专业团队]
    CUSTOM[用户创建与客制化团队] --> TEAMDEF[角色、工具、步骤与偏好]
    TEAMDEF --> TEAM
    TEAM --> ROLES[专业角色与实际产物交接]
    ROLES --> TOOLS[工具注册、授权与调用]
    TOOL --> TOOLS
    TOOLS --> DOC[文档编写、HTML 生成、PDF 查看等]
    TOOLS --> CAREER[岗位、简历、面试、追踪能力]
    CAREER --> EDITOR[专业工作台]
    MAIN --> RUN[任务、计划版本与执行记录]
    ROLES --> RUN
    TOOLS --> RUN
    DIRECT --> OUTPUT[回复、进度与产物卡片]
    RUN --> OUTPUT
    EDITOR --> OUTPUT
    OUTPUT --> CHAT
~~~

这是目标架构。主 Agent 的能力选择、团队定制、通用工具接口与执行记录关联仍需实现；既有聊天和求职工作台是复用基础。

### 4.2 核心对象与执行约束

| 对象 | 责任与边界 |
| --- | --- |
| MainAgent | 持续对话、能力选择、上下文、协调与最终回复 |
| Conversation | 消息、当前任务、资料和产物引用、会话摘要；可承载多个任务 |
| AgentDefinition | 专业角色职责、指令、工具与输入输出约定 |
| Team | 用途、版本、角色、工具、步骤和输出偏好；创建与调用分开 |
| ToolDefinition | 输入输出、动作影响、权限与执行接口；可直接调用或被团队复用 |
| Plan / Task | 版本、步骤、负责人、输入、依赖、状态和产物；不强制每个任务有团队 |
| Run | 会话、任务、可选团队版本、计划版本、执行预算、状态与检查点；独立于聊天页面，可暂停和恢复 |
| Artifact | 文档、HTML、PDF 等产物的内容、位置、来源、版本和审阅状态 |
| Event / Handoff | 执行者、动作、输入输出引用、时间和状态 |
| Context | 当前会话、资料选择和授权范围，按任务提供必要内容 |
| ExecutionRequest / Checkpoint | 接单记录、排队顺序、恢复位置、尝试次数和操作凭据；防止重复派发与重复保存 |
| TaskEvent / Delivery | 持久化进度事件与结果交付记录；驱动会话、任务入口和通知，交付状态与已读状态分离 |

配置、会话与运行分别管理。团队配置确认不等于批准未来所有写操作。直接工具任务的团队引用允许为空，团队任务绑定已选择版本。工具结果、产物证据与必要确认决定状态；依赖失败不能按成功交接。

### 4.3 从现有实现迁移

- 保持 Agent 聊天入口、富卡片与流式回复，补充团队和工具调用及产物继续编辑。
- 求职规划与执行保留领域实现，通过适配层服务主 Agent 和简历团队。
- 盘点工具的读取、分析、生成、预览和保存边界，定义可复用输入输出。
- 复用既有确认、证据和恢复约束，关联会话、直接工具任务、团队运行与产物。
- 保留简历编辑、HTML 转 PDF、面试与追踪工作台，打通返回原会话和任务。

通用层与领域层边界以真实代码确定，不预设现有求职运行时已支持通用团队编排。

### 4.4 后台执行与交付边界

后台执行器拥有运行生命周期，聊天 ViewModel 负责展示状态及提交命令；不能把聊天协程改名为“后台任务”即视为完成。任务接单、检查点、产物、交付与通知均需持久化并可核验。

首版目标是在手机正常运行、所需网络和系统执行条件满足时，切应用和锁屏后继续完成任务；系统回收后从可靠检查点恢复，结果未知的写操作先核验。关机后继续执行不属于产品需求，不扩展相关服务端方案；强行停止和断网按中断与恢复处理。

普通聊天仍使用 `viewModelScope` 启动回复。2026-11-25 已加入文档草稿与可选 HTML 的独立后台服务、持久队列、通知入口，以及可复用团队的创建、编辑、选用和工作要求快照。当前由单个主 Agent 使用配置，不代表多个角色独立执行的通用团队运行时；设备行为仍待验收，详见 [后台文档实现进展](AGENT_BACKGROUND_IMPLEMENTATION.md)。PDF 导出仍依赖主线程 WebView 和打印适配器，其无页面运行能力需要单独验证。目标方案及验收矩阵见 [后台委托与结果交付规格](AGENT_BACKGROUND_EXECUTION_SPEC.md)。

## 5. 首版需求与验收

| 优先级 | 需求 | 验收标准 |
| --- | --- | --- |
| P0 | 主 Agent 聊天首页 | 冷启动进入对话；可输入、附加资料及继续交流，不先跳到团队配置 |
| P0 | 连续任务上下文 | “继续修改”“换版式”引用正确资料与产物；退出后恢复原会话和任务 |
| P0 | 直接处理与工具调用 | 没有自建团队也可回答或使用已接入工具；展示实际状态和结果 |
| P0 | 专业团队调用 | 主 Agent 可选择简历团队，用户可主动指定；结果回到同一对话 |
| P0 | 创建与客制化团队 | 生成配置草案；可调整职责、工具、顺序与偏好，确认保存不自动运行 |
| P0 | 可追溯协作 | 必要的多角色顺序协作读取真实上游产物，失败阻塞后续依赖 |
| P0 | 简历端到端验证 | 对话串联读取、分析、内容、版式及预览；首版范围以实际工具为准 |
| P0 | 产物审阅与确认 | 草稿自动可靠保存，采用或正式资料变更按已有授权处理；恢复不重复提交已确认写操作 |
| P0 | 对话内进度与干预 | 显示当前动作、错误及待确认项；可停止、重试、展开详情 |
| P0 | 灵感直接委托 | 明确委托后按交付约定推进草稿；无自建团队也可执行，讨论和仅记录不误启动 |
| P0 | 后台执行与排队 | 任务脱离页面生命周期；切应用和锁屏实测继续，连续委托有持久队列，等待用户时释放执行位 |
| P0 | 通知与阶段成果 | 步骤变化和新成果保存后更新通知，能看到当前动作与已有成果；查看成果不停止执行，完成、需处理和失败准确区分，拒绝权限有应用内替代 |
| P0 | 可靠结果交付 | 产物可打开后再标完成；重复事件、重进页面和重复点通知不重复交付或重跑，未读结果可找回 |
| P0 | 中断与预算 | 断网、回收、暂停、取消有明确状态；检查点和凭据恢复不重复写入，超出执行预算等待用户决定 |
| P1 | 第二场景验证 | 同一主 Agent 完成阅读整理，不依赖求职字段 |
| P1 | 专业编辑器返回 | 打开文档、HTML 或 PDF 界面，返回后继续处理正确产物 |

首版团队以简单顺序协作为主，角色数量不作为用户完成普通任务的门槛。

### 5.1 暂不纳入首版

任意复杂 DAG 画布、条件分支、循环、并行调度、跨设备同步、任意代码执行、任意网站访问、外部账号操作、自动投递、第三方市场和多用户协作。服务端托管执行、手机关机后继续计算及定时周期任务暂不纳入。只对已接入且验证过的工具标明后台可用能力。

### 5.2 信任与数据管理

- 不默认把完整会话记忆和全部资料提供给每个团队，按任务和授权提供必要内容。
- 草稿生成与任务空间持久化可按委托直接推进；采用、保存到正式资料及覆盖分别定义，已有授权继续有效，新增影响按具体动作处理。
- 模型建议与工具结果区分，待确认任务不计为完成；失败和恢复保留原因及版本。
- 执行记录关联会话、团队版本与产物来源；日志避免无必要的敏感资料复制。
- 用户可查看和删除会话、团队、任务与资料；删除影响和模型服务数据边界在实现时明确。

## 6. 迭代顺序与验证

1. 先验证“说出委托 → 可靠接单 → 离开聊天仍执行 → 通知看到进度 → 回来接收结果 → 继续修改”。
2. 定义交付约定、工具能力和运行状态，建立独立执行器、持久队列、事件与检查点。
3. 打通最小文档草稿任务的后台交付，再整合简历工具链；单独验证无页面 PDF 导出和版本一致性。
4. 完成通知、待处理、拒绝权限、断网、系统回收与重复派发验收，再扩大支持工具范围。
5. 验证用户团队工作方式的保存、主动指定、推荐调用与版本管理。
6. 用灵感方案或用户提供文本验证跨场景复用，检查求职字段硬编码。

待建立基线的指标：首条需求获得有效回复或产物的比例、后台任务交付率、离开页面后的完成率、通知到正确结果的到达率、等待用户比例、恢复成功率、重复操作率、连续修改成功率、团队复用率。后台交付率需按完成、缺资料、系统限制、失败和用户取消拆分，不能将所有离开页面的任务都算成功。

## 7. 待讨论事项

- 会话记忆与个人偏好如何选择、查看和删除？
- 第二场景是否采用阅读整理，具体工具范围如何确定？
